# P3-E27-A2 Close Report — Fix UID Linking Race Condition
**Date:** 2026-06-22
**Epic:** P3-E27-A2 (sub-phase of P3-E27 Employee Onboarding System)
**Priority:** P0 — production race condition on every new hire login
**Strategy executed:** Strategy 1 — Full `onStaffRegistered` callable (atomic Auth + claims + Firestore)

---

## Summary

Eliminated the client-side email-migration race condition in `StaffAuthProvider.tsx`. Every new
staff hire's Firebase Auth UID now matches their Firestore document ID from the moment of
registration. The `onStaffRegistered` Cloud Function owns the entire lifecycle atomically — Auth
account creation, custom claims, and `staff/{uid}` Firestore write — in a single server-side
operation. The client-side `addDoc()` path is gone.

## Race Condition — Before vs After

**Before:**
1. Lauren: `addDoc(collection(db, 'staff'), data)` → random doc ID (e.g. `xK9mP...`)
2. Employee logs in → Firebase Auth UID (e.g. `abc123`)
3. `StaffAuthProvider` snapshot: `staff/abc123` → doesn't exist
4. `isLinking = true` → email query → `setDoc(staff/abc123)` → `deleteDoc(staff/xK9mP...)` — all async, no atomicity
5. If token refresh fires during step 4 → second `onSnapshot` → `isLinking` already `true` but second copy completes before first → duplicate write or orphaned doc

**After:**
1. Lauren: `httpsCallable('onStaffRegistered', input)` → CF runs server-side
2. CF: `auth.createUser()` → UID `abc123` → `setCustomUserClaims()` → `db.doc('staff/abc123').set(...)`
3. Employee logs in → `staff/abc123` already exists → snapshot delivers profile instantly
4. No migration, no race window
