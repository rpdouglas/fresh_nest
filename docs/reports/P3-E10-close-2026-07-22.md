## What this epic actually closed
The referral program's scaffolding (code generation, redemption UI, sharing UI, marketing copy) was already live and shipped, but never touched money — no discount was ever applied to a Stripe charge, no credit was ever issued, and there was no ledger, no customer-facing balance, and no admin management screen. This epic makes the program financially real: **$20 referrer / $20 referee** (human-confirmed, matching Accepted ADR-009 and the already-live customer copy).

## Work Done

1. **Schema**: `referrals.ownerEmail` (added at code-gen time), `config/referralConfig` (configurable reward amounts, public-read/admin-write), `credits` collection (customer ledger, zero client writes — server/callable-only).
2. **Referee-side discount**: `createPaymentIntent` (`functions/src/callable/payments.ts`) now applies the discount if a referral code is already known at intent-creation time. Since the intent is actually created *before* the customer can type a code (a real ordering quirk discovered during implementation — `BookingStep4.tsx`'s promo field renders in the same step the PaymentIntent is eagerly created for), a new `applyReferralDiscount` callable updates the *already-created* PaymentIntent's amount once a code is verified — the common real-world case. The price summary now shows a "Referral discount" line so what the customer sees matches what Stripe actually charges (closing a real UX inconsistency this investigation surfaced, not just a missing feature).
3. **Referrer-side credit issuance + redemption finalization**: both folded into the *existing* `onBookingStatusConfirmed` trigger (not a new parallel trigger, a deliberate refinement from the drafted plan — see below) — issues one `credits` doc to the referrer (idempotent, keyed on `sourceBookingId`) and finalizes any credits *this* booking's payer spent (read from the captured PaymentIntent's `metadata.appliedCreditIds`, no second Stripe call needed).
4. **Admin credit management**: new `adjustCredit` callable (`functions/src/callable/referrals.ts`, admin-gated, audit-logged) + new `RewardsManager.tsx` admin screen (modeled on `PayRatesManager.tsx`) — view all credits, issue a manual credit, revoke an available one.
5. **Customer rewards view**: new `/account/rewards` tab (`CustomerRewardsPage.tsx`) — own code/share link (reuses `ThankYouPage.tsx`'s share-card markup), credit history, available balance.
6. **Referral lifecycle fix**: `onBookingCancelled` now deactivates the referral code owned by a cancelled booking — closes the exact gap ADR-009's own "Consequences" section flagged as unresolved.

## Refinements from the drafted AGY plan (found during implementation, not scope changes)
- **Credit issuance and redemption-finalization were folded into the existing `onBookingStatusConfirmed` trigger, not a new parallel trigger.** The drafted plan proposed a separate trigger (matching D2/D3's "business workflow vs. audit logging" split), but that split was about separating *concerns*; here, both new behaviors *are* the same concern — "settle this booking's financial consequences now that it's truly confirmed" — the same moment the existing trigger already captures the Stripe payment. Two independent triggers both listening for the same status transition on the same document would have been the worse design, not the better-separated one.
- **Credits are "reserved" at PaymentIntent creation but only marked `redeemed` at booking-confirmation time**, not in the same call that computes the discount. Reason: `submitBooking()` doesn't create the actual booking document until *after* Stripe payment is confirmed client-side, and the booking isn't truly `confirmed` (payment captured) until an admin acts on it later. Burning a customer's credit the moment they *start* checkout — before they've even submitted the form — would permanently lose it on an abandoned session. This wasn't spelled out in the drafted plan's Key Tasks list; found by tracing the actual booking flow's timing.

## Firestore Rules — NOT DEPLOYED, awaiting human review
Per the approved plan and `docs/COMPLIANCE.md`'s explicit prohibition on AI agents autonomously deploying `firestore.rules` changes, both `firestore.rules` and `firestore.dev.rules` have new blocks for `config/referralConfig` (public read, admin write) and `credits` (admin read all / customer read own via `request.auth.token.email == resource.data.customerEmail` / **zero writes from any client, ever** — `allow write: if false`). These files have been edited on disk but **no `firebase deploy` command has been run**. This needs explicit sign-off before it goes live — until then, the new Cloud Functions code will work in production (Admin SDK bypasses rules), but a customer's `/account/rewards` page and the admin `RewardsManager` screen will fail to read `credits`/`referrals`/`config` documents against the *currently deployed* rules, since those don't exist there yet.

## Known Follow-Ups (not blocking this epic's close)
- **`firestore.rules`/`firestore.dev.rules` deploy is pending explicit human approval** — the single most important open item from this epic. Nothing in production reads/writes these new collections without it (Cloud Functions use the Admin SDK and are unaffected).
- No settings UI was built for editing `config/referralConfig` — it's admin-write-capable via the new rules, but Lauren/the dev team would edit the reward amounts via the Firestore console directly for now. The epic's own key task only required "configurable, not hardcoded," not a dedicated settings screen; building one wasn't asked for and would have been scope creep.
- Credits are consumed in whole units (no partial/change-making) — if a customer's available credit exceeds a booking's remaining total after discount, the excess is not preserved for a future booking. A reasonable simplification given all credits are currently equal $20 increments; would need revisiting if `adjustCredit` ever issues non-$20 manual amounts at scale.
- `npm run test:rules` (Firestore emulator) was not run in this environment — the new rules are reasoned through manually, not emulator-verified. Worth running before or immediately after the deploy sign-off.
