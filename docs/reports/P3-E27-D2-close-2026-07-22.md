## Work Done

2. **`onStaffStatusActivated`** (new Firestore trigger, `functions/src/triggers/staff.ts`): fires on `before.status !== 'active' && after.status === 'active'`, guarded on `after.probation` still being `null` so an `active → inactive → active` reactivation never overwrites an in-progress record. Writes `startDate`/`endDate` (+90 days) and 3 check-ins at Day 30/60/90, then sends a bilingual "Congratulations, you're active!" email in the employee's `preferences.language`.
3. **`onProbationCheckInDue`** (new scheduled fn, `functions/src/scheduled/probation.ts`, daily 9am UTC, mirrors `onDailyReminderCheck`'s exact shape): queries `staff` where `probation.probationOutcome == 'pending'`, filters each employee's `checkIns` in code for `scheduledDate === today && completedDate == null`, and emails + SMS's Lauren per due check-in (reusing `sendOwnerNotification`-style `config.ownerEmail` and the `process.env.OWNER_PHONE` SMS-to-admin pattern from `onBookingCancelled`).
4. **Probation Tracking section in `StaffDetailPanel.tsx`**: three check-in cards (complete/overdue/due-today/upcoming computed from today vs. `scheduledDate`/`completedDate`), each expandable to a complete-check-in form (date, 1–5 rating, notes). Outcome buttons (Passed/Extended/Terminate) enabled only once all check-ins are complete. "Extend 90 Days" appends 3 new check-ins and resets `probationOutcome` to `'pending'`; "Terminate" only flips `status: 'inactive'` (D3's future trigger reacts to that transition — not built here, matching D1's precedent for "Activate Employee").
5. **`useStaff.ts`**: `completeCheckIn` (whole-array `probation.checkIns` write, matching `ProfilePage.tsx`'s `blockedWindows` pattern), `setProbationOutcome`, `extendProbation` — all direct `updateDoc`, no new callable (`isAdmin()` already grants unrestricted write access, confirmed in D1).
6. **`onStaffUpdatedTrigger`**: extended to diff `probation.checkIns` completions (per check-in, keyed by `id`) and `probation.probationOutcome` changes for `auditLog`, matching the existing diff pattern.
7. **`adminEmail` threaded through**: `AdminPage.tsx` → `StaffTable.tsx` → `StaffDetailPanel.tsx`, reusing the existing `user.email` already available from `useAdminAuth()` (same convention as `BookingsTable`'s `adminEmail` prop) rather than a second `onAuthStateChanged` subscription, to populate `completedBy` on completed check-ins.
8. **Email templates**: `probationActivationSubject/Html` (employee-facing, bilingual, `functions/src/emailTemplates.ts`) and `probationCheckInDueSubject/Text` (Lauren-facing, English-only, matching `ownerSubject/ownerText`).
9. **Schema doc**: `docs/firestore-schema.md` updated with the full `probation` field description.

## Scoped down from the original narrative spec
Per the approved plan: a **separate `onStaffStatusActivated` trigger** (not folded into `onStaffUpdatedTrigger`, which stays a pure audit-logging concern) and **"Terminated" only transitions `status` to `'inactive'`** — the narrative's "trigger offboarding checklist" is P3-E27-D3's own `onStaffDeactivated` trigger, deliberately not built here, same forward-scoping pattern used at the D1→D2 boundary.

**One implementation simplification versus the drafted spec**: check-in `label` (e.g. `"Day 30"`) is *not* stored as English text on the document — check-ins store a numeric `dayOffset: 30 | 60 | 90` instead, and the admin panel derives the display label via `t('...checkInLabel', { day: checkIn.dayOffset })`. This avoids baking untranslated UI text into Firestore and matches the codebase's existing pattern of fixed-ID-keyed labels (`TRAINING_MODULE_ORDER`). Documented in `docs/firestore-schema.md`.
