## Reactivation policy decisions (human-confirmed)
1. Reactivation lands the employee directly in `status: 'active'` (trusting historical clearances), not back through `'onboarding'`.
2. Reactivation resets `probation` and `offboarding` to a clean slate (`null`), treating it as a new employment period — `onStaffStatusActivated` naturally reinitializes a fresh 30/60/90 window.

## Work Done

1. **Schema**: `offboarding: { deactivatedAt, checklist: { authRevoked, keysReturned, accessCodesChanged, finalPayCalculated, recordArchived }, finalNotes, departureReason } | null` added to `Staff`.
2. **`onStaffDeactivated`** (new Firestore trigger, `functions/src/triggers/staff.ts`): fires on `!= 'inactive' -> 'inactive'`. Calls `auth.updateUser({disabled: true})`, `auth.setCustomUserClaims({role: 'inactive'})`, and **`auth.revokeRefreshTokens()`** — the third call is beyond the source narrative doc's literal 2-step list, added because `disabled: true` alone only blocks *new* sign-ins; an already-issued ID token stays valid until its own expiry (up to ~1hr) without an explicit refresh-token revocation. Writes a fresh `offboarding` block (fully overwritten on every deactivation, not guarded like probation's "already initialized" check — each departure is its own event), emails Lauren, and logs a specific `auditLog` entry for the Auth revocation.
3. **`reactivateStaff`** (new admin-gated callable, `functions/src/callable/staff.ts`): re-enables the Auth account, restores the role-mapped custom claim (same mapping `onStaffRegistered` uses), and resets `status: 'active'`, `probation: null`, `offboarding: null`. Built as a callable rather than a direct client write — restoring Auth access requires real Firebase Auth Admin API calls a browser `updateDoc` cannot make.
4. **Offboarding section in `StaffDetailPanel.tsx`** (visible only when `status === 'inactive'`): `authRevoked` shown read-only with the deactivation timestamp; 3 admin toggles (keys returned, access codes changed, final pay calculated); departure reason selector; final notes textarea; Reactivate button.
5. **Status Management gating fix**: D1's plain "Activate Employee" button — which only ever does `updateDoc({status: 'active'})` — is now hidden for `inactive` staff and replaced with a pointer to the new Reactivate flow. Without this fix, clicking the old button on a deactivated employee would have flipped the Firestore flag to `'active'` while the Auth account stayed disabled, silently leaving them locked out.
6. **`StaffAuthProvider.tsx`**: `signInWithPassword` and `completeMagicLinkSignIn` now catch `auth/user-disabled` specifically and surface a real, translated `fsm.login.errorDeactivated` message ("Your account has been deactivated. Contact Fresh Nest Co.") instead of the generic invalid-credentials/general error. Real EN + FR + AR locale-file entries added (this login area is fully translated in all three FSM languages, unlike the admin-only `defaultValue`-only convention).
7. **`onStaffUpdatedTrigger`**: extended to diff `offboarding.checklist` toggles, `finalNotes`, and `departureReason` for `auditLog`.

## Narrative doc reconciliation
The source narrative's D3 section lists only `updateUser({disabled: true})` and `setCustomUserClaims({role: 'inactive'})` as the Auth-revocation steps — genuinely missing `revokeRefreshTokens`. Since "closing the security gap where former employees retain valid Firebase Auth sessions" is the epic's own stated objective, this was a real gap in the drafted spec, not an optional scope addition, and was added during Phase A planning before any code was written.
