# P3-E27-C1 — First-Login Consent Sequence

## Parent Epic
- **P3-E27**: Employee Onboarding System

## Objective
Replace the current ad-hoc stack of independently-mounted overlays (`LanguageSelectionOverlay`, `BackgroundCheckConsentScreen`, `TermsConsentOverlay`) with a single `OnboardingSequenceGuard` that renders exactly one screen at a time, in a defined order, with a visible "Step X of 4" progress indicator. Adds the two remaining legally-required steps — Employment Agreement (Ontario ESA) and Emergency Contact (OHSA) — closing the last of the four legal gates this epic exists to fix.

## Background — current state has a real sequencing bug
Today, `FsmLayout.tsx` mounts three overlays independently, each deciding for itself whether to show, stacked by hardcoded z-index (`LanguageSelectionOverlay` z-50, `TermsConsentOverlay` z-50, `BackgroundCheckConsentScreen` z-60). A brand-new employee with no language set, no background check consent, and no terms accepted will see **`BackgroundCheckConsentScreen` render on top of `LanguageSelectionOverlay`** (z-60 beats z-50), meaning they can be asked to consent to a background check in a language they never chose. `OnboardingSequenceGuard` fixes this by making step order an explicit, deterministic list instead of a z-index race.

## Personas
- **P8 Jasmine Beausoleil (Cleaner)**: guided, mobile-first first login — must complete the full sequence in under 10 minutes without confusion about what's next.
- **P11 Brenda Côté (Lead Cleaner, French-primary)**: must see all four screens entirely in French, chosen correctly on Screen 0 before anything else renders.
- **P13 Marcus Oakes (Part-time student)**: needs the sequence to be fast, with zero unnecessary friction, and resumable if he closes the app partway through.

## Key Tasks
1. **`OnboardingSequenceGuard`** (`apps/fsm/src/components/auth/`): inserted into the router tree between `ProtectedRoute` and `FsmLayout` (`apps/fsm/src/App.tsx`). Reads `staffProfile.preferences.language`, `staffProfile.employmentAgreement?.acceptedAt`, `staffProfile.backgroundCheck?.consentGiven`, `staffProfile.compliance?.acceptedTermsVersion`, `staffProfile.emergencyContact?.name` and renders the first incomplete step; once all are complete, renders `<Outlet />` (the real FSM app, unchanged).
2. **Step order**: Language Selection (prerequisite, not counted in "Step X of 4") → Step 1 Employment Agreement → Step 2 Background Check Consent (existing `BackgroundCheckConsentScreen`, reused as-is) → Step 3 Platform Terms (existing `TermsConsentOverlay`, reused as-is) → Step 4 Emergency Contact.
3. **Remove** the three ad-hoc mounts (`LanguageSelectionOverlay`, `BackgroundCheckConsentScreen`, `TermsConsentOverlay`) from `FsmLayout.tsx` — they move into the guard's step list. `TermsConsentOverlay`'s own internal logic (version-outdated re-prompt for *returning* employees) is preserved, since the guard only fully bypasses Step 3 if the currently accepted version matches.
4. **New `EmploymentAgreementScreen`**: bilingual scrollable agreement text (`t()` keys), "type your full name to sign" input, checkbox, progress indicator. On accept, writes `staffProfile.employmentAgreement: { version, acceptedAt, signedByName, ipAddress }`.
5. **New `EmergencyContactScreen`**: name / relationship / phone fields, progress indicator. On save, writes `staffProfile.emergencyContact: { name, phone, relationship }`.
6. **Resumability**: each screen saves to Firestore before advancing (already true for Background Check and Terms); if Jasmine closes the app after Screen 2, she resumes at Screen 3 next login, not Screen 1 — this falls directly out of the guard re-evaluating which step is first-incomplete on every render.
7. **Shared types/schema**: add `employmentAgreement` and `emergencyContact` to `Staff` (`packages/shared/src/types/staff.ts`), parsed in `staffConverter`; document both in `docs/firestore-schema.md`.
8. **`firestore.rules`**: add `employmentAgreement` and `emergencyContact` to the self-service `hasOnly()` allowlist on `staff/{staffId}` (both are fully employee-writable, unlike `backgroundCheck` — no admin-only sub-fields), consistent with how `compliance` is already handled.
9. **i18n**: all new copy in `fsm.compliance.employmentAgreement.*` and `fsm.compliance.emergencyContact.*`, EN/FR (AR not required by this epic's acceptance criteria).

## Schema Changes
### `staff` Collection
- `employmentAgreement`: `{ version: string, acceptedAt: Timestamp, signedByName: string, ipAddress: string | null } | null` — new field.
- `emergencyContact`: `{ name: string, phone: string, relationship: string } | null` — new field. (Narrative source doc originally proposed nesting under `personalDetails.emergencyContact`; this project has no `personalDetails` map anywhere else in the schema, so this spec places it top-level for consistency with every other `staff` field — flagged for confirmation in the Phase A plan.)
