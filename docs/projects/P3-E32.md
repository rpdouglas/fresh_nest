## Goal

Lauren (P12) can add, replace, reorder, publish and remove before/after photo pairs from her phone,
with no developer and no deploy. Every photo comes out in one uniform format.

## Human decisions (2026-10-04)

1. Strategy 2: a Gallery tab on the admin page.
2. The five existing pairs were placeholders — dropped.
3. Client consent is recorded by a tick box on the upload form.
4. Admin only. Lead cleaners do not upload.

## What was built

- **Gallery tab** on `/admin`: add a pair (service, EN + FR caption, before and after photo, consent
  tick), then publish/unpublish, show on home page, move up/down, edit, delete.
- **Photo fitting in the browser** (`apps/customer/src/lib/utils/imageProcessing.ts`): rotates the
  photo upright, crops the largest square at a position chosen with a slider, scales to 1200×1200
  (never upscaled), re-encodes as JPEG at 80%. Re-encoding through a canvas drops all embedded
  metadata, including GPS location. Photos under 600px on the short side are refused.
- **Storage:** photos upload to `gallery/{pairId}/before-{timestamp}.jpg` and `after-{timestamp}.jpg`.
- **Firestore:** `galleryPairs` collection — see `docs/firestore-schema.md` section 13.
- **Public pages** (`/gallery`, home preview, lightbox) read published pairs from Firestore and show
  the caption in the visitor's language. New pairs start unpublished.
- The placeholder photos and the hard-coded pair list are removed.
- The gallery stays hidden on the public site (`SHOW_GALLERY = false`, P3-E31) until switched on.

## Security rules

### 1. `firestore.rules` and `firestore.dev.rules` — ✅ approved by human and deployed 2026-10-04

```
    // P3-E32: before/after gallery pairs
    match /galleryPairs/{pairId} {
      // Anyone can read published pairs; admins can read all
      allow read: if resource.data.published == true || isAdmin();
      allow create, update, delete: if isAdmin();
    }
```

Before deploying, the live rules for both databases were downloaded and compared with the repo:
identical, so the deploy added only this block. Covered by four tests in
`apps/customer/test/firestore-rules.test.ts`, passing against both rule files in the emulator.

### 2. Storage rules — ⏸ waiting on human approval

The human asked to use the existing Storage rules if possible. It is not possible: the rules live
in the Firebase console (released 2026-05-23) deny everything:

```
    match /{allPaths=**} {
      allow read, write: if false;
    }
```

`storage.rules` in the repo now holds those rules plus one block for the gallery. It is **not
deployed**, and CI does not deploy it.

```
    match /gallery/{pairId}/{fileName} {
      allow read: if request.auth != null && request.auth.token.role == 'admin';
      allow write: if request.auth != null
                   && request.auth.token.role == 'admin'
                   && (request.resource == null
                       || (request.resource.size < 1 * 1024 * 1024
                           && request.resource.contentType == 'image/jpeg'));
    }
```

This is tighter than the public-read rule in the plan. Only admins can read or write through the
rules; visitors load photos through the download URLs saved on each pair, which Firebase serves
without consulting the rules. `request.resource == null` covers deletes.

To apply once approved: `npx firebase deploy --only storage --project freshnest-aa51e`.

Until then the Gallery tab loads and lists pairs, but saving a pair fails at the upload step with
"The pair could not be saved".

### Side finding — staff job photos (not part of this epic)

The same deny-all rules cover `jobs/{jobId}/photos/{photoId}`, where the staff app uploads job
photos (`apps/fsm/src/context/OfflineUploadProvider.tsx`). If the staff app uses this bucket
(`freshnest-aa51e.firebasestorage.app`, the only one with rules released), those uploads are being
refused in production. Not verified against a real upload. This needs its own decision and rule;
nothing was changed for it here.

## Verification so far

- Type-check, ESLint on changed files, unit tests and `npm run build` pass.
- Photo fitting run in a real browser (Chromium) on generated 4032×3024, 3024×4032 and 1200×900
  images: output is 1200×1200 JPEG (900×900 for the small one, not upscaled), about 110–220 KB,
  cropped at the chosen position; a 500×400 image, a HEIC file and a corrupt file are refused with
  the right message.
- Pair form rendered at 375px: all controls are at least 48px tall, no horizontal scroll.
- **Not yet verified:** the Gallery tab against real Firebase (sign-in, upload, publish, delete).
  That needs the Storage rule above. It also has not been tried on a physical iPhone or Android phone.
