# P3-E10 — Loyalty & Referral Reward Loop

## Objective
Turn the referral program's existing scaffolding into an actual two-sided reward: a new client who books with a valid referral code gets $20 off immediately, and the referrer earns a $20 credit toward their next booking once the referred booking is confirmed. Give Lauren a management view to see and adjust credits, and give customers a place to see their own code, referral history, and balance.

## What already exists vs. what's genuinely new
The referral program isn't new — it's half-built, and has been since ADR-009 (Accepted, 2026-06-13):
- **Code generation** — `onBookingCreated` already writes a deterministic code (`FIRSTNAME-LAST4`) to a public-read `referrals/{code}` collection and back onto the booking (`functions/src/triggers/booking.ts`).
- **Code redemption UI** — `BookingStep4.tsx` already lets a new client type in a code, verifies it live against `referrals/{code}`, and stores it as `referredBy` on their booking.
- **Sharing UI** — `ThankYouPage.tsx` already shows the new client their own code and a shareable link.
- **Copy** — `en.json`/`fr.json` already promise **"$20 off"** to both sides in the `referrals.*` namespace.
- **Admin visibility** — `BookingDetailPanel.tsx` already shows `referredBy`/`referralCode` as read-only badges; `AnalyticsDashboard.tsx` already tallies a platform-wide `referredBookingsCount`.

**What's genuinely new**: none of the above ever touches money. No discount is ever subtracted from a Stripe `PaymentIntent`. No credit is ever issued to a referrer. There is no credit ledger anywhere in the schema, no per-customer reward view, no admin credit-management screen, and no configurable reward amount (nothing but marketing copy states $20 anywhere in code).

## Personas
- **P1 Diane Lafleur**: an active referrer within her francophone Cornwall community — the reward loop needs to work correctly in French, since her network is where referrals actually originate.
- **P2 Travis McLeod**: explicitly price-sensitive, named in the epic's own narrative-doc section — responds to discounts, not brand storytelling. The referee-side $20 discount needs to be visible and unambiguous before he pays, not a surprise after.
- **P4 Kahnawà:ke Baptiste** (secondary): the Akwesasne location page's feature-requirements table already mentions a referral program — its copy needs to stay consistent with whatever ships here.
- **P12 Lauren Arsenault** (secondary): needs a credit-management view and an audit trail for any financial-field change, per the codebase's established "financial field writes get audit-logged" pattern (already used for `financials.monthlyEarningsLimit` in `onStaffUpdatedTrigger`).

## Reward amount — resolved
**$20 referrer / $20 referee**, confirmed by the human, matching the Accepted ADR-009 and the already-live customer-facing copy — not the separate master-plan doc's untested "$25/$25" recommendation, which would have required rewriting published EN/FR copy and reconciling against an immutable Accepted ADR.

## Key architecture decisions
1. **`credits` is a money ledger, not a checklist — nothing writes to it directly from the client, not even admin.** D1/D2/D3 established a precedent of admin-only booleans being safe for direct `updateDoc` writes because `isAdmin()` already grants unrestricted access and the fields carry no server-side bounds. That precedent doesn't extend to a collection holding literal dollar amounts that feed a live Stripe charge calculation — every mutation (issue, redeem, admin-adjust, admin-revoke) goes through a callable, each of which also writes `auditLog`.
2. **Reward amount is configurable, not hardcoded**, via a new `referralConfig` document — matches the epic's own key task and avoids a second deploy every time the dollar figure changes.
3. **Separate trigger for credit issuance, not folded into `onStaffUpdatedTrigger`'s audit-logging shape** — same "business workflow vs. audit logging" split already used for `onStaffStatusActivated`/`onStaffDeactivated`.
4. **`firestore.rules` changes are required and must be flagged for explicit human review before deploy.** Unlike D1–D3 (which needed zero rules changes), `credits` and `referralConfig` are new collections that need real rules — and `docs/COMPLIANCE.md` explicitly prohibits AI agents from deploying `firestore.rules` changes autonomously. This is a named, called-out artifact for sign-off in Phase B, not a silent detail.
5. **Closing a real gap ADR-009 itself already flagged**: referral codes aren't deactivated when the booking that owns them is cancelled. Extending the existing `onBookingCancelled` trigger to flip `referrals/{code}.active = false` closes it, in the same spirit as D2/D3's "fix a real bug while in the neighborhood" pattern.
6. **No new marketing notification is built.** The acceptance criteria (below) don't require an email/SMS when a credit is earned, and building one would raise CASL opt-in questions (a proactive "you earned a reward" nudge could read as marketing, unlike a purely transactional confirmation) that are out of scope unless requested. Deferred, not silently dropped.

## Key Tasks
1. **Schema**: `referralConfig` (single config doc: `referrerRewardAmount`, `refereeDiscountAmount`, `currency`, `enabled`); `credits` collection (`customerEmail`, `amount`, `currency`, `reason`, `sourceBookingId`, `sourceReferralCode`, `status: 'available' | 'redeemed' | 'revoked'`, `issuedAt`, `redeemedAt`, `redeemedOnBookingId`, `adjustedBy`). Extend `referrals/{code}` with `ownerEmail` at creation time.
2. **Referee-side discount + referrer-side redemption**: extend `createPaymentIntent` (`functions/src/callable/payments.ts`) to subtract the referee discount (if `referredBy` is valid) and the paying customer's own available credits from the Stripe `amount`, marking redeemed credits atomically in the same call.
3. **Referrer-side credit issuance**: new trigger reacting to `bookings.status -> 'confirmed'` with `referredBy` set, idempotent per booking, issuing one `credits` doc to the referrer.
4. **Admin credit management**: new admin-gated `adjustCredit` callable (manual adjust/revoke, audit-logged) and a new admin Rewards screen listing all credits.
5. **Customer rewards view**: new `/account/rewards` tab in the existing `CustomerPortalLayout.tsx` tab set — code/share link, credit history, available balance.
6. **Referral lifecycle fix**: extend `onBookingCancelled` to deactivate the owned referral code.
7. **i18n**: admin Rewards screen follows the D1–D3 `defaultValue`-only convention; the customer-facing `/account/rewards` tab needs real EN/FR entries (existing `customerPortal.*` namespace is fully translated, matching precedent).

## Acceptance Criteria
- [ ] A booking with a valid, active referral code has its Stripe `PaymentIntent` amount reduced by exactly $20.
- [ ] When that referred booking's `status` transitions to `confirmed`, the referrer receives exactly one $20 credit within 60 seconds — never duplicated on repeated status writes.
- [ ] The referrer's own next `createPaymentIntent` call reflects their available credit balance, and the consumed credit is marked `redeemed` with the booking it was applied to.
- [ ] Credit balance and referral history are visible in the customer portal.
- [ ] Admin can view all credits and manually adjust or revoke one; the action is logged to `auditLog`.
- [ ] Cancelling the booking that owns a referral code flips that code's `active` to `false`.
- [ ] No client-side write (customer or admin) can create, modify, or delete a `credits` document directly.
- [ ] Code builds cleanly and lint checks pass with zero errors.

## Schema Changes
### New: `referralConfig` (single document, e.g. `config/referralConfig`)
- `referrerRewardAmount: number` (CAD, e.g. `20`), `refereeDiscountAmount: number` (CAD, e.g. `20`), `currency: 'CAD'`, `enabled: boolean`. Public-read (booking wizard needs it pre-checkout), admin-only write.

### New: `credits` collection
- `customerEmail: string`, `amount: number`, `currency: 'CAD'`, `reason: 'referral_reward' | 'admin_adjustment'`, `sourceBookingId: string | null`, `sourceReferralCode: string | null`, `status: 'available' | 'redeemed' | 'revoked'`, `issuedAt: Timestamp`, `redeemedAt: Timestamp | null`, `redeemedOnBookingId: string | null`, `adjustedBy: string | null`. No direct client writes (customer or admin) — callable-only. Customer can read only their own (`request.auth.token.email == resource.data.customerEmail`).

### `referrals` collection (extend)
- Add `ownerEmail: string` at creation time in `onBookingCreated`, alongside the existing `ownerName`/`bookingId`/`active`/`createdAt`.
