# P3-E27-D1 — Staff Detail Panel & Onboarding Checklist UI

## Parent Epic
- **P3-E27**: Employee Onboarding System

## Objective
Give Lauren a complete, real-time view of every employee's onboarding status and the ability to take every required admin-side compliance action from the admin panel — without a direct Firestore edit. This is the epic every prior C-band sub-epic (B2, C1, C2, C3) explicitly deferred admin visibility to.

## Personas
- **P12 Lauren Arsenault (Admin/Owner)**: needs one place to see and act on every employee's onboarding status — background check, signed agreement, training progress, and the manual items (ID verified, uniform issued, etc.) that have no employee-facing counterpart.

## What already exists vs. what's genuinely new
Four sub-epics have already shipped real functionality this narrative-doc section (written before they existed) assumed would still need to be built:
- **Background check status editor** — already fully built in `StaffTable.tsx` (P3-E27-B2): an inline status/provider/notes editor calling `updateBackgroundCheckStatus`, which already writes to `auditLog`.
- **Employment agreement** — already exists (`employmentAgreement.signedByName`/`acceptedAt`, P3-E27-C1), just not yet surfaced in the admin UI.
- **Compliance overview data** (terms version/date/IP, background check consent date/IP, emergency contact) — all already exist as real fields, just not yet displayed together anywhere in admin.
- **Training progress** — all 6 module flags + `platformTrainingCompleted` already exist (P3-E27-C3), just not yet displayed.

**What's genuinely new in this epic**: `idVerified`, `supervisedShiftCompleted`, `uniformIssued`, `directDepositOnFile` (four admin-only booleans with no prior epic touching them), the "Activate Employee" button and its gating, and the expandable panel UI itself.

## Key architecture decisions

1. **Reuse the existing row-expansion pattern.** `BookingsTable.tsx` already expands a row into a `BookingDetailPanel` via `AnimatePresence` — this epic follows the identical pattern: `StaffTable.tsx` gains a click-to-expand row → `StaffDetailPanel.tsx` (new), rather than inventing a new UI convention.
2. **Consolidate, don't duplicate, the background check editor.** The inline editor B2 built directly in `StaffTable.tsx`'s row cells moves into the new `StaffDetailPanel` alongside the other checklist items, so Lauren has one place for all onboarding actions instead of two. `StaffTable.tsx`'s row keeps a compact read-only status badge (as it does today) that opens the panel on click.
3. **Audit logging via the existing trigger, not a new callable.** Admin already has unrestricted write access to `staff` docs via `isAdmin()` in `firestore.rules` — no rules change is needed for the four new admin-only booleans. `onStaffUpdatedTrigger` (which already diffs `compliance`, `status`, `role`, and `financials.monthlyEarningsLimit`) gets four more tracked fields, matching the established pattern exactly rather than introducing a parallel callable-based audit path.
4. **"Activate Employee" only transitions `status`.** The narrative spec has this button also write `probation.startDate`/`endDate` and generate check-in entries — that's P3-E27-D2's schema and its own Firestore trigger (`onStaffStatusActivated`). This epic's button does nothing more than flip `status: 'onboarding' → 'active'` once gating conditions are met; D2 reacts to that transition independently when it's built. Keeps D1 shippable on its own without a half-built probation feature.
5. **SIN field is out of scope for this epic — flagged, not silently dropped.** The narrative spec's `personalDetails.sin` masked field is real Social Insurance Number PII with specific Canadian legal handling requirements (encryption at rest, restricted access, never logged) that `docs/COMPLIANCE.md` doesn't currently address at all (and is the stalest core reference doc in the project, per the earlier governance review). Collecting SIN without that groundwork first would be a compliance risk, not a convenience feature. **Recommendation: defer entirely, revisit only after a COMPLIANCE.md update and likely its own ADR.**

## Key Tasks
1. **`StaffDetailPanel.tsx`** (new, `apps/customer/src/components/admin/`), modeled on `BookingDetailPanel.tsx`, with sections:
   - **Onboarding Checklist**: employment agreement (read-only, from C1), background check consent (read-only, from B2) + status editor (moved from `StaffTable.tsx`), training progress (read-only, from C3, module-by-module with completion dates), and the four new admin-toggle items (ID Verified, Supervised Shift Completed, Uniform Issued, Direct Deposit on File).
   - **Compliance Overview**: terms version/date/IP, background check consent date/IP, emergency contact (read-only display).
   - **Status Management**: "Activate Employee" button, disabled with a tooltip until `backgroundCheck.status === 'cleared'`, `idVerified === true`, `employmentAgreement !== null`, and `onboardingChecklist.platformTrainingCompleted === true`.
   - **Quick Actions**: "Resend Welcome Email" (reuses the existing `resendWelcomeEmail` callable from B1) and "Export Staff Record" (reuses the existing `ExportRecordModal`, unchanged).
2. **`StaffTable.tsx`**: add row-click-to-expand wired to `StaffDetailPanel` (`AnimatePresence`, matching `BookingsTable.tsx`); remove the now-redundant inline background-check editor added in B2 (superseded by the panel).
3. **Schema**: add `onboardingChecklist.idVerified`, `.supervisedShiftCompleted`, `.uniformIssued`, `.directDepositOnFile` (all `boolean`, admin-only) — no rules change needed (`isAdmin()` already has unrestricted write access).
4. **`onStaffUpdatedTrigger`**: add the four new fields to the existing diff-and-audit-log logic.
5. **i18n**: all new admin-panel strings via `t()` — EN/FR (this is admin-facing, not FR-required by any persona test the way employee-facing screens are, but the codebase's convention has been full EN/FR parity everywhere regardless, and Lauren's UI already is bilingual today).

## Acceptance Criteria
- [ ] Lauren can view every employee's complete onboarding status without leaving the admin panel.
- [ ] Lauren can mark background check cleared from the panel, and the dispatch board immediately stops warning about that employee (already true today via B2 — this just relocates the UI, doesn't change the underlying behavior).
- [ ] "Activate Employee" is disabled with a tooltip until background check cleared, ID verified, employment agreement signed, and platform training complete.
- [ ] All four new admin checklist toggles write to `auditLog` via `onStaffUpdatedTrigger`.
- [ ] Training progress and compliance overview display real data, not placeholders.
- [ ] All new strings use `t()` — Linguistic_Auditor verified; Brand_Auditor confirms design-token compliance.
- [ ] Code builds cleanly and lint checks pass with zero errors.

## Schema Changes
### `staff` Collection
- `onboardingChecklist.idVerified`, `.supervisedShiftCompleted`, `.uniformIssued`, `.directDepositOnFile`: `boolean`, admin-only (written via direct `updateDoc` from an authenticated admin session — already permitted, no rules change).
