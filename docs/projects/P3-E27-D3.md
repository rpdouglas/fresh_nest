# P3-E27-D3 — Structured Offboarding

## Parent Epic
- **P3-E27**: Employee Onboarding System

## Objective
When an employee's `status` transitions to `'inactive'`, automatically revoke their FSM access and valid sessions, generate an offboarding checklist, and notify Lauren — closing the real, currently-live security gap where a deactivated employee's Firebase Auth account (and any already-issued session) keeps working indefinitely. This is the final sub-epic of P3-E27 — closing it completes the whole Employee Onboarding System.

## Personas
- **P12 Lauren Arsenault (Admin/Owner)**: needs deactivation to actually mean "this person can no longer see client addresses or job schedules," plus a lightweight checklist (keys, access codes, final pay) so nothing falls through the cracks.
- **P8 Jasmine Beausoleil (Cleaner)** / all staff: if deactivated, sees a clear, human message ("Contact Fresh Nest Co.") instead of a confusing generic login error.

## Real security gap this closes
Today `status` can only reach `'inactive'` via D2's "Terminate" outcome button (or, previously, a direct Firestore edit) — and nothing reacts to it. The employee's Firebase Auth account stays enabled and their custom claims stay valid, so **any already-signed-in session keeps working**, and they can sign in again at will. This is a live gap in the shipped app, not a hypothetical.

## Narrative doc reconciliation
The source narrative doc's D3 section lists 2 Auth calls on deactivation (`updateUser({disabled: true})`, `setCustomUserClaims({role: 'inactive'})`) but **omits `auth.revokeRefreshTokens(uid)`**. Without it, `disabled: true` blocks *new* sign-ins but does not invalidate an ID token the employee already holds — Firebase only re-checks `disabled` on token refresh (up to ~1 hour later), so a currently-logged-in former employee could keep using the FSM app for up to an hour after deactivation. Since "closing the security gap where former employees retain valid Firebase Auth sessions" is this epic's own stated objective, `revokeRefreshTokens` is added as a third, non-optional step — flagging this explicitly since it's a real gap in the drafted spec, not a scope addition for its own sake.

## Key architecture decisions
1. **Separate trigger, not folded into `onStaffUpdatedTrigger`.** Same reasoning as D2's `onStaffStatusActivated`: this is a business workflow (Auth API calls) reacting to one specific transition, not an audit-logging concern. `onStaffDeactivated` fires on `before.status !== 'inactive' && after.status === 'inactive'`.
2. **`offboarding` is fully overwritten on every transition into `'inactive'`** (not guarded like D2's "already initialized" check) — each deactivation is a fresh departure event, so a stale checklist from a *previous* departure (in the reactivate → re-deactivate case) should not persist into the new one.
3. **Reactivation requires a new callable, not a direct client write.** Unlike D1/D2's checklist toggles (plain Firestore fields, safe for `isAdmin()` + direct `updateDoc`), reversing a deactivation means calling `auth.updateUser(disabled: false)` and restoring custom claims — real Firebase Auth Admin API calls only the Admin SDK can make. New `reactivateStaff` callable (admin-gated, same `isAuthorized` pattern as `resendWelcomeEmail`).
4. **D1's plain "Activate Employee" button must be hidden/blocked once `status === 'inactive'`.** That button does a bare `updateDoc({status: 'active'})` — it would flip the Firestore field back to `'active'` without ever re-enabling the Auth account, silently leaving the employee locked out despite the UI claiming they're active. `StaffDetailPanel`'s Status Management section needs a third branch (onboarding / active / **inactive**) pointing inactive employees to the new Offboarding section's "Reactivate" button instead.
5. **`recordArchived` is schema-only, not built.** The narrative describes it as "set automatically by annual archival" — that's P3-E15 (Data Retention & PIPEDA Right-to-Erasure), a separate, not-yet-started epic. Field is added to the schema for forward compatibility (permanently `false` today, no admin toggle, no archival job), matching the same "defer to the epic that owns it" pattern already used for the SIN field (D1) and offboarding-triggering (D1→D2).
6. **`docs/COMPLIANCE.md` still doesn't address data retention for offboarded employee records** — flagged again (previously flagged in the original governance review), not addressed by this epic. This epic revokes *access*; it does not touch data retention/erasure, which is P3-E15's job.

## Open questions for human approval

### 1. Reactivation destination: straight to `active`, or back through `onboarding`?
The narrative's "Reactivate" button restores Auth access and clears `offboarding.deactivatedAt`, landing the employee directly back in `status: 'active'` — trusting their historical background check / training / agreement as still valid. The alternative is landing them in `status: 'onboarding'`, forcing a full re-verification cycle (new background check, ID re-verification, training) before they can work again.

**This plan defaults to direct-to-`active`** (matches the narrative doc, fastest rehire path, and D2's `onStaffStatusActivated` trigger already handles "give them a fresh 30/60/90 probation window" for free — see decision below). Flagging because this is a real security/HR-policy tradeoff, not just an engineering choice: a `performance`-terminated rehire skipping re-verification may not be what Lauren wants.

### 2. Does reactivation restart probation and clear offboarding history?
Not addressed by the narrative doc at all (written before P3-E27-D2 existed). This plan's recommendation: **yes** — `reactivateStaff` resets both `probation: null` and `offboarding: null` before setting `status: 'active'`, so D2's existing `onStaffStatusActivated` trigger naturally reinitializes a fresh 30/60/90 window, treating reactivation as a new employment period. The alternative is preserving the old probation/offboarding record and not restarting probation tracking. Flagging alongside Q1 since the answer to Q1 (if `onboarding`) makes this moot — probation would restart naturally once they're re-activated through the normal path.

## Key Tasks
1. **Schema**: `offboarding: { deactivatedAt: Date | null, checklist: { authRevoked, keysReturned, accessCodesChanged, finalPayCalculated, recordArchived }, finalNotes: string | null, departureReason: 'voluntary' | 'performance' | 'seasonal' | 'other' | null } | null` on `staff`.
2. **`onStaffDeactivated`** (new Firestore trigger, `functions/src/triggers/staff.ts`): fires on `!= 'inactive' -> 'inactive'`. Calls `auth.updateUser(uid, {disabled: true})`, `auth.setCustomUserClaims(uid, {role: 'inactive'})`, `auth.revokeRefreshTokens(uid)`; writes a fresh `offboarding` block (`deactivatedAt: now`, `checklist.authRevoked: true`, all other checklist items `false`, `finalNotes`/`departureReason` cleared for admin to fill in); sends Lauren an English-only notification email (matches `ownerSubject`/`ownerText`'s admin-alert precedent); logs a specific `auditLog` entry for the Auth revocation (`field: 'offboarding.checklist.authRevoked'`), separate from `onStaffUpdatedTrigger`'s existing generic `status` diff entry.
3. **`reactivateStaff`** (new admin-gated callable, `functions/src/callable/staff.ts`): `auth.updateUser(uid, {disabled: false})`, restores custom claims from `staff.role` (same `role === 'supervisor' ? 'supervisor' : 'staff'` mapping `onStaffRegistered` already uses), writes `status: 'active'`, `probation: null`, `offboarding: null` (pending Q2 answer).
4. **Offboarding section in `StaffDetailPanel.tsx`** (visible only when `status === 'inactive'`): `authRevoked` shown read-only with `deactivatedAt` timestamp; 3 admin toggles (`keysReturned`, `accessCodesChanged`, `finalPayCalculated` — same closed-union direct-write pattern as D1's `AdminChecklistItem`); departure reason selector; final notes textarea; "Reactivate" button (calls the new callable).
5. **Status Management gating fix**: hide/disable D1's plain "Activate Employee" button when `status === 'inactive'`, pointing to the new Reactivate flow instead (see decision #4).
6. **`StaffAuthProvider.tsx`**: catch `auth/user-disabled` in both `signInWithPassword` and `completeMagicLinkSignIn`, surface a new, real (not defaultValue-only — this is the employee-facing login screen, an already-fully-translated area) `fsm.login.errorDeactivated` message in both `en.json`/`fr.json`, instead of the generic `errorInvalid`/`errorGeneral`.
7. **`onStaffUpdatedTrigger`**: extend to audit-log `offboarding.checklist` toggles, `finalNotes`, and `departureReason` changes, matching the existing diff pattern.
8. **i18n**: `admin.staff.detail.offboarding.*` follows D1/D2's established `defaultValue`-only convention (admin-only namespace); `fsm.login.errorDeactivated` gets real EN + FR entries (employee-facing login area, already fully translated).

## Acceptance Criteria
- [ ] When status transitions to `'inactive'`, the employee cannot sign in (password or magic link) — new attempts get `auth/user-disabled`.
- [ ] An already-signed-in deactivated employee's session is invalidated (not just blocked from new sign-in) via `revokeRefreshTokens`.
- [ ] A deactivated employee attempting to sign in sees a clear "Your account has been deactivated. Contact Fresh Nest Co." message, not a generic error.
- [ ] Lauren receives an email confirming the deactivation.
- [ ] The Auth revocation is logged to `auditLog`.
- [ ] Offboarding checklist (keys returned, access codes changed, final pay calculated) is visible and editable in `StaffDetailPanel` only for `inactive` staff.
- [ ] D1's "Activate Employee" button no longer appears/functions for `inactive` staff — only the new "Reactivate" button does.
- [ ] Reactivation fully restores FSM access (Auth re-enabled, correct role claim restored) within 60 seconds.
- [ ] Code builds cleanly and lint checks pass with zero errors.

## Schema Changes
### `staff` Collection
- `offboarding`: `{ deactivatedAt: Timestamp | null, checklist: { authRevoked: boolean, keysReturned: boolean, accessCodesChanged: boolean, finalPayCalculated: boolean, recordArchived: boolean }, finalNotes: string | null, departureReason: 'voluntary' | 'performance' | 'seasonal' | 'other' | null } | null` — `null` until first deactivation; written by `onStaffDeactivated` (fully overwritten on each new deactivation event) and thereafter by admin (`StaffDetailPanel`, direct write, same trust model as D1/D2) for the 3 manual checklist items, `finalNotes`, `departureReason`. `checklist.authRevoked` is trigger-set only, never admin-editable. `checklist.recordArchived` is schema-only, always `false`, no UI — deferred to P3-E15.
