# P3-E27-D2 — 30/60/90 Day Probation Tracking

## Parent Epic
- **P3-E27**: Employee Onboarding System

## Objective
Automatically schedule and track structured probation check-ins for every newly-activated employee, alerting Lauren by SMS and email when one is due, giving Fresh Nest Co. both an early-warning system for struggling employees and documented evidence of managerial engagement during the critical first 90 days.

## Personas
- **P12 Lauren Arsenault (Admin/Owner)**: needs structured, reminded follow-up — not to rely on memory for who's due a check-in.
- **P8 Jasmine Beausoleil (Cleaner)**: benefits from being formally checked in on, not left to sink or swim after activation.
- **P11 Brenda Côté (Lead Cleaner, French-primary)**: any employee-facing notification (the activation congratulations email) must be in her language.

## Open question for human approval: check-in cadence
The source narrative doc (`docs/reports/freshnest-employee-onboarding-project-plan.md`) is **internally inconsistent** about the actual check-in schedule: the epic's own name (and its title in `docs/ACTIVE_CYCLE.md`) says "30/60/90 Day," but the "Key Tasks" section specifies generating "Day 5 (first check-in after ~first five shifts), Day 30, Day 90," and the admin-panel mockup describes "three check-in cards (Day 5 / Day 30 / Day 90)."

**This plan defaults to the epic's own name — Day 30 / Day 60 / Day 90** — since it's the far more standard, recognizable HR review cadence, matches what's actually documented as this epic's title everywhere else in the project, and a reasonable reader would expect "30/60/90 Day Probation Tracking" to mean exactly that. The "Day 5" idea (an early check-in after the first ~5 shifts) is a reasonable addition on its own merits but is a different concept — an early-warning shift-count trigger, not a calendar-day probation review — and would need its own design (shift-count tracking, not date-math). **Flagging explicitly rather than silently picking one**: confirm 30/60/90 is correct, or say if a 4th early check-in (Day 5) should be added.

## Key architecture decisions
1. **Separate trigger, not folded into `onStaffUpdatedTrigger`.** `onStaffUpdatedTrigger` is an audit-logging concern (record what changed); probation initiation is a business workflow reacting to one specific transition (`status: 'onboarding' → 'active'`). Keeping them as separate Firestore triggers on the same document path (Firestore supports multiple independent triggers per path) keeps each function single-purpose and matches the narrative's own naming (`onStaffStatusActivated`).
2. **Trigger-based, not client-written.** Probation fields are generated by a Firestore trigger reacting to the status transition, not written by D1's `activateEmployee` client call — this preserves D1's explicit scoping decision (that function does only the status transition) and means probation initialization works regardless of *how* status ever transitions to `'active'` in the future (not just through today's one button).
3. **Check-in completion: direct admin write of the whole `checkIns` array**, matching the established pattern already used for `constraints.blockedWindows` in `ProfilePage.tsx` (read the array client-side, update the matching entry, write the whole array back). No new callable — admin already has unrestricted `staff`-doc write access (confirmed in D1), and this is a single-admin, low-concurrency editing context, the same profile as blocked windows.
4. **"Terminated" outcome only transitions `status` to `'inactive'`.** The narrative has this also "trigger offboarding checklist" — that's P3-E27-D3's `onStaffDeactivated` trigger, not yet built. Matches the exact same forward-scoping pattern already used between D1 and this epic: each epic transitions `status`, the next epic's own trigger reacts to it.
5. **Reminder delivery reuses established infrastructure exactly**: `onProbationCheckInDue` follows the identical `onSchedule({schedule, timeZone, secrets})` shape as the existing `onDailyReminderCheck`; the SMS-to-Lauren path reuses the `process.env.OWNER_PHONE || '<fallback>'` pattern already used in `triggers/booking.ts`'s cancellation alert; the email-to-Lauren path reuses the existing `sendOwnerNotification`-style `config.ownerEmail` pattern from `sendEmail.ts`.

## Key Tasks
1. **Schema**: add `probation: { startDate: string, endDate: string, checkIns: Array<{ id, scheduledDate, label, completedDate, notes, rating, completedBy }>, probationOutcome: 'pending' | 'passed' | 'extended' | 'terminated' | null } | null` to `staff`.
2. **`onStaffStatusActivated`** (new Firestore trigger, `functions/src/triggers/staff.ts`): fires when `before.status !== 'active' && after.status === 'active'`. Writes `probation.startDate` (today), `probation.endDate` (+90 days), generates 3 `checkIns` entries (Day 30/60/90 pending confirmation above), sends a bilingual "Welcome, you're active!" email to the employee (reusing the existing `sendEmail`/template infrastructure, language from `preferences.language`).
3. **`onProbationCheckInDue`** (new scheduled function, `functions/src/scheduled/probation.ts`, daily 9am): queries `staff` where any `probation.checkIns[].scheduledDate == today && completedDate == null`, sends Lauren an email + SMS per due employee.
4. **Probation section in `StaffDetailPanel.tsx`**: three check-in timeline cards (upcoming/due/overdue/complete status per card computed from today's date vs. `scheduledDate`/`completedDate`), each expandable to a "Complete check-in" form (date picker defaulting today, notes textarea, 5-star rating). Probation outcome selector (Passed/Extended/Terminated) enabled once all 3 check-ins are complete. "Extended" appends 90 more days and 3 new check-ins to the existing array; "Terminated" sets `status: 'inactive'` only (see decision #4 above).
5. **`onStaffUpdatedTrigger`**: extend to audit-log `probation.checkIns` completions and `probation.probationOutcome` changes, matching the existing diff pattern.
6. **i18n**: activation congratulations email (EN/FR, employee-facing — Brenda-critical); admin panel copy follows the established `admin.staff.*` `defaultValue`-only convention (D1 precedent).

## Acceptance Criteria
- [ ] On an employee's activation, `probation.startDate`/`endDate` and 3 check-in entries are generated within 60 seconds.
- [ ] Lauren receives an email + SMS reminder on each check-in's due date.
- [ ] Lauren can complete a check-in with notes and a 1–5 rating from the Staff Detail Panel; the completion is logged to `auditLog`.
- [ ] Probation outcome flows correctly: "Passed" requires no further action; "Extended" generates 3 new check-ins 90 days out; "Terminated" sets `status: 'inactive'`.
- [ ] The activation email sends in the employee's `preferences.language`.
- [ ] Code builds cleanly and lint checks pass with zero errors.

## Schema Changes
### `staff` Collection
- `probation`: `{ startDate: string, endDate: string, checkIns: Array<{ id: string, scheduledDate: string, label: string, completedDate: string | null, notes: string | null, rating: 1|2|3|4|5|null, completedBy: string | null }>, probationOutcome: 'pending' | 'passed' | 'extended' | 'terminated' | null } | null` — `null` until an employee is first activated; written by `onStaffStatusActivated` and thereafter by admin (via `StaffDetailPanel`, direct write, same trust model as D1's checklist toggles).
