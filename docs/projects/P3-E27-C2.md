# P3-E27-C2 — Employee Self-Service Profile Completion

## Parent Epic
- **P3-E27**: Employee Onboarding System

## Objective
Expand the FSM `ProfilePage.tsx` to let employees maintain their own contact details, flag data-entry corrections, view their role/status, set their language preference, and edit the emergency contact collected in P3-E27-C1 — closing the gap where an employee can't fix a typo'd phone number or confirm Lauren typed their name correctly without calling her.

## Personas
- **P13 Marcus Oakes (Part-time student)**: needs to update his phone number and manage his availability without calling Lauren — his blocked-windows self-service already exists; this epic extends the same self-service principle to contact details.
- **P8 Jasmine Beausoleil (Cleaner)**: her emergency contact (collected during C1's first-login sequence) should be visible and editable here if it changes.

## Background — what already exists vs. what's missing
`ProfilePage.tsx` today has 4 cards: read-only Personal Details (name/email/phone/role — **all read-only, including phone**), Transit & Commute Constraints (editable), Blocked Windows (editable), and an ODSP Earnings Tracker where the **employee already self-sets their own `financials.monthlyEarningsLimit`** via a direct `updateDoc` — this has been live since before this epic. Missing: phone editing, a status badge, a language-preference control, a "flag a correction" channel for anything else, and an editable Emergency Contact section (the field now exists as of C1, but nothing in the FSM app lets the employee see or edit it after their first login).

## Open decision for human approval before Phase B
The original narrative source doc (`docs/reports/freshnest-employee-onboarding-project-plan.md`) lists `financials.monthlyEarningsLimit` as one of the fields that should become **read-only / admin-only** as part of this epic. That conflicts with the already-shipped `ProfilePage.tsx` behavior (Card 4), which lets the employee set it themselves — and CLAUDE.md's own persona table only credits Marcus with "self-managed **blocked windows**," not a self-managed earnings cap. **This plan defaults to leaving the current self-editable behavior unchanged** (out of scope for C2) since locking it down would be a functional regression to already-shipped, tested code with no bug report driving it — but flags it explicitly so a human can override if the self-set earnings limit was never actually intended.

## Key Tasks
1. **"My Details" section**: add a status badge (Onboarding / Active / Inactive, read-only) next to the existing role badge; add a language-preference `<select>` (en/fr/ar) writing `preferences.language` — already permitted by `firestore.rules`, just needs UI.
2. **"Contact" section**: make `phone` an editable input (currently read-only display text); add a "Flag a correction" free-text field that appends `{ text, flaggedAt }` to a new `corrections` array field (visible to Lauren; full admin UI for reviewing corrections is out of scope here, deferred to P3-E27-D1's Staff Detail Panel).
3. **"Emergency Contact" section**: new card, pre-filled from `staffProfile.emergencyContact` (set during C1), editable name/phone/relationship — reuses the same field the C1 `EmergencyContactScreen` writes.
4. **Availability / Earnings**: unchanged — already implemented and working (see Open Decision above for the one field whose future is in question).
5. **`firestore.rules`**: add `phone` and `corrections` to the `staff/{staffId}` self-service `hasOnly()` allowlist. `preferences` and `emergencyContact` are already permitted from prior epics.
6. **Schema**: add `corrections: Array<{ text: string, flaggedAt: Timestamp }>` to the `Staff` type and `docs/firestore-schema.md`.
7. **`onStaffUpdatedTrigger`**: add a 5th tracked field (`phone`) to the existing audit-log diffing logic in `functions/src/triggers/staff.ts`, alongside the existing terms/status/role/earnings-limit tracking — `changedBy` should reflect the employee's own uid for self-service phone edits (unlike status/role/earnings-limit, which are always admin-attributed today).

## Acceptance Criteria
- [ ] Marcus can update his phone number without calling Lauren; the change is reflected immediately and logged to `auditLog`.
- [ ] Jasmine's emergency contact (from C1) is pre-filled in her profile and editable.
- [ ] Language preference change updates the FSM UI language immediately.
- [ ] "Flag a correction" appends to `corrections` without touching any other field.
- [ ] Read-only fields (name, email, role, status) cannot be changed by the employee — verified by the existing `hasOnly()` allowlist never including `firstName`/`lastName`/`email`/`role`/`status`.
- [ ] All new strings use `t()` — Linguistic_Auditor verified.
- [ ] Code builds cleanly and lint checks pass with zero errors.

## Schema Changes
### `staff` Collection
- `corrections`: `Array<{ text: string, flaggedAt: Timestamp }>` — new field, employee-writable (append-only in practice via the UI, though the rule itself only restricts the top-level key, not append-vs-replace semantics).
