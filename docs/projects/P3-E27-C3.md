# P3-E27-C3 — Platform Training Modules

## Parent Epic
- **P3-E27**: Employee Onboarding System

## Objective
Build a structured, bilingual training module system in the FSM app covering six essential knowledge areas — including Ontario's legally-required WHMIS chemical safety training — before a new employee can be assigned jobs independently. Today `onboardingChecklist.trainingCompleted: false` is a boolean with no content, no module, and no mechanism to ever become `true`.

## Personas
- **P8 Jasmine Beausoleil (Cleaner, new to field service apps)**: needs guided, mobile-friendly training she can complete in under 45 minutes.
- **P11 Brenda Côté (Lead Cleaner, French-primary)**: must complete every module entirely in French.
- **P13 Marcus Oakes (Part-time student)**: wants training available as a **quick reference** afterward, not a one-time locked gate — implies modules should stay accessible and browsable in any order, not just during onboarding.

## Adapting the original narrative spec to what's already built
`docs/reports/freshnest-employee-onboarding-project-plan.md`'s C3 section (written before B2/C1 shipped) proposes expanding `onboardingChecklist` into a 15-field object duplicating data that already exists in richer form:
- `backgroundCheckConsent`/`backgroundCheckCleared` → already `backgroundCheck.consentGiven`/`backgroundCheck.status === 'cleared'` (P3-E27-B2).
- `contractSigned` → already `employmentAgreement !== null` (P3-E27-C1).
- `emergencyContactCollected` → already `emergencyContact !== null` (P3-E27-C1).
- `idVerified`, `supervisedShiftCompleted`, `uniformIssued`, `directDepositOnFile` → admin-only manual checklist items with no employee-facing UI of their own; these belong to **P3-E27-D1**'s Staff Detail Panel, not this epic — no reason to invent the schema for them now (JIT scoping, not speculative).

**This epic adds only what training modules actually need**: `onboardingChecklist.module1Welcome` … `module6EmergencyProcedures` (booleans) and `onboardingChecklist.platformTrainingCompleted` (auto-computed when all 6 are `true`).

## Key architecture decision: keep `onboardingChecklist` closed to direct client writes
`onboardingChecklist` is **not** currently in the `staff/{staffId}` self-service `hasOnly()` allowlist. The narrative doc's own plan for D1 will eventually add admin-only fields (`idVerified`, `supervisedShiftCompleted`, etc.) into this **same map** — the exact "employee-writable + admin-only fields mixed in one map" shape that made a direct client `hasOnly()` addition unsafe for `backgroundCheck` in B2. To avoid needing to retrofit nested-diff rules logic later when D1 lands, this epic follows the **B2 precedent**: a dedicated callable (`completeTrainingModule`) is the only way an employee can flip a module flag, and `onboardingChecklist` stays outside the client-writable allowlist.

## Key Tasks
1. **Training content** (`apps/fsm/src/lib/data/trainingModules.ts`, new): a static config array of 6 modules, each with an id, an i18n key prefix, an ordered list of content-section keys, and 3 comprehension-check questions (each with an i18n key, answer-choice keys, and a correct-answer index). Mirrors the `locationData.ts`-style "config array + i18n key references" pattern already used in the customer app — no hardcoded content strings, no new Firestore collection.
2. **New callable `completeTrainingModule`** (`functions/src/callable/staff.ts`): employee-only, scoped to `request.auth.uid`, accepts `{ moduleId }`, validates it's one of the 6 known module ids, writes `onboardingChecklist.{moduleId}: true`, and sets `onboardingChecklist.platformTrainingCompleted: true` in the same update if all 6 are now complete (read-modify-write against the current doc).
3. **New `TrainingPage`** (`apps/fsm/src/pages/TrainingPage.tsx`, route `/training`): a module list (checkmarks for completed modules, WHMIS visually flagged as legally required) that opens a selected module's content + 3-question comprehension check inline. "I've completed this module" only enables once all 3 questions are answered correctly. **Free-order, not sequential** — matches Marcus's "quick reference" need and the WHMIS module's standalone legal urgency; modules stay accessible after completion for review, satisfying the "moves to Resources" spirit of the narrative doc without needing a separate nav section.
4. **`FsmLayout` nav**: add a "Training" link (`/training`) to `navLinks`.
5. **Dispatch WHMIS gate**: extend `checkCleanerSchedulingConflicts` (`apps/customer/src/lib/utils/scheduling.ts`) and `DispatchBoard.tsx`'s proactive conflict badges with a check for `onboardingChecklist?.module4Whmis !== true`, reusing the exact warning + admin-override + `auditLog` mechanism already established for the B2 background-check gate — no new plumbing needed, just one more condition in the same functions.
6. **Schema**: document the 8 new `onboardingChecklist` keys in `docs/firestore-schema.md`.
7. **i18n**: all training content, quiz questions, and answer choices via `t()` — EN/FR (AR not required by this epic's acceptance criteria, consistent with B2/C1's scoping).

## Acceptance Criteria
- [ ] Jasmine can complete all 6 modules on mobile; each comprehension check requires all 3 answers correct before the module can be marked complete.
- [ ] Brenda completes every module entirely in French (Linguistic_Auditor verified — zero hardcoded strings).
- [ ] An employee cannot mark a module complete for anyone but themselves (`completeTrainingModule` scoped to `request.auth.uid`).
- [ ] `onboardingChecklist.platformTrainingCompleted` becomes `true` automatically once all 6 modules are done — no separate action required.
- [ ] Dispatch board blocks assigning a job to an employee whose `module4Whmis` isn't complete, with the same override-and-audit-log flow as the existing background-check gate.
- [ ] Modules remain accessible and reviewable after completion (Marcus's quick-reference need).
- [ ] Code builds cleanly and lint checks pass with zero errors.

## Schema Changes
### `staff` Collection
- `onboardingChecklist.module1Welcome` … `module6EmergencyProcedures`: `boolean` — set exclusively by the `completeTrainingModule` callable.
- `onboardingChecklist.platformTrainingCompleted`: `boolean` — auto-computed by the same callable when all 6 module flags are `true`.

## Dependencies
- P3-E27-C1 ✅ (first-login sequence should complete before training, per the narrative's intended flow — not hard-enforced by a guard in this epic, since training access isn't itself a legal gate the way the C1 screens are).
- P3-E27-D1 (deferred): admin visibility into per-module completion status, and the remaining admin-only checklist fields (`idVerified`, `supervisedShiftCompleted`, `uniformIssued`, `directDepositOnFile`) — this epic deliberately leaves room for them in the same `onboardingChecklist` map without needing rework.
