# P3-E37 — Audit Everywhere (Wave 0, W0-3)

**Type:** Platform / compliance · **Priority:** P1 · **Complexity:** M–L
**Opened:** 2026-10-28 · **Status:** 🔄 Phase A — Planning (owner decisions recorded; plan awaiting approval)
**Plan:** [`plans/P3-E37_PLAN.md`](../plans/P3-E37_PLAN.md) · **Source:** [FSM gap analysis](../gap-analysis/GAP_ANALYSIS_2026-10-27.md) W0-3, MP-S5.12, CE-S6.2; spec §0 rule 4 ("facts are append-only") and rule 12 ("everything audited")

## Why
The spec's wave 0 exit test is *"every change is audited"*. Today only role changes, policy changes, conflict overrides (written from the browser) and four staff fields (with `changedBy: 'admin'` hard-coded) are audited. Booking and job changes, checklists, pay rates, the gallery and deletions leave no trace. Any office user can also create audit rows from the browser, so the log can be skipped or faked.

## Owner decisions (2026-10-28)
1. **Where entries are written — server triggers + a `lastChange` stamp (option A).**
   - One Firestore trigger per audited collection compares the record before and after each write and writes the audit entry.
   - Every app save stamps `lastChange = { by, at, source, reason?, overrideType? }`. The rules check that `by` is the signed-in person's email and `at` is the request time.
   - Server code stamps `by: 'system:<function>'`, or the caller's email when a callable acts for a person.
2. **Lock the audit log.** `auditLog` becomes read-only for apps: Owners and Managers can read; nobody can create, update or delete from an app. Only server code writes. Override reasons and types reach the log through `lastChange.reason` / `lastChange.overrideType` on the job/booking save.
3. **What is audited:**
   - **Bookings:** status, date/time, address, service, notes/access info, assignment, checklist template.
   - **Jobs:** status, assigned cleaner, scheduled date/time, attached checklist, check-in/out times.
   - **Staff:** status, role, earnings limit, terms, availability/blocked windows, contact details. This replaces the current staff trigger's hard-coded `'admin'`.
   - **Saved checklists:** create, edit, archive.
   - **Pay rates:** every change.
   - **Gallery:** create, publish/unpublish, featured, delete.
   - **Reviews:** approve/reject.
   - **Deletions:** a full snapshot whenever an audited record is deleted.
   - Settings and Team & roles are already audited and stay as they are.
4. **Not audited:**
   - individual checklist ticks and photo uploads (the job already keeps them with timestamps);
   - notification read flags.
   - Starting and completing a job *is* audited (status).
5. **Entry shape: one entry per save.** New fields `actor`, `source`, `action` (`create` | `update` | `delete`) and `changes: [{ field, before, after }]`. Existing one-field rows (`field`, `oldValue`, `newValue`) stay valid and still display.
6. **Screens:**
   - a **History** section on each booking (booking panel), job (Dispatch card / booking panel) and staff profile;
   - **Audit Logs** filters by record, person, source and date range, and a search by booking/job ID.
   - Office (Owner/Manager) only, EN/FR, 48 px targets, phone-friendly.
7. **Retention: 7 years**, the same as bookings. The rule is recorded now; the automatic clean-up and erasure anonymizing are built with **P3-E15**.
8. **Out-of-date apps — tolerant 2 weeks, then strict.**
   - At first the rules accept a save with **no** `lastChange` (logged as *"unknown — older app version"*) but reject a `lastChange` naming someone else.
   - About 2 weeks after release, a follow-up PR makes `lastChange` required for app writes.

## Acceptance criteria / persona tests
- **Lauren reschedules a booking** (date + cleaner in one save): one audit entry with her email, source *Admin panel*, and both changes old → new. It appears in that booking's **History**.
- **Override with a reason on the Dispatch Board:** the entry carries the reason and override type, and the Audit Logs override filter still finds it.
- **Brenda (FR) starts and completes a job in the staff app:** two entries, actor Brenda, source *Staff app*. The History reads in French when the admin panel is in French.
- **A customer cancels from the portal:** entry with the customer's email, source *Customer portal*.
- **A public quote request:** a `create` entry, source *Public quote form*.
- **Server-side changes** (e.g. renewals, `claimJob`): attributed to `system:<function>` or to the claiming staff member, never to the last person who edited by hand.
- **Deleting a gallery pair:** a `delete` entry with the full snapshot.
- **Rules tests:**
  - no app can create, update or delete `auditLog`;
  - a save with `lastChange.by` ≠ the signed-in email is denied;
  - a save without `lastChange` is allowed during the tolerant period;
  - a save whose `lastChange.at` ≠ request time is denied.
- **Old one-field audit rows** still display correctly in Audit Logs.
- **Unit tests** for the diff engine: watched fields only; nested fields; arrays; timestamps; unchanged saves write nothing; delete snapshots.

## Out of scope
- **Automatic deletion after 7 years and erasure anonymizing:** P3-E15.
- **Audit of record *views*** (e.g. who opened an agreement): W1-5 / agreements.
- **Undo from the audit log:** W0-6 / scheduling (`scheduleChanges`).
- **Making `lastChange` required:** a follow-up PR about 2 weeks after release.
